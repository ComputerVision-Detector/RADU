# 텍스트 줄 bbox 정답 라벨링 설계안

> 상태: 사용자가 기존 라벨링 앱 확장 방식을 선택함. 최종 설계 승인 후 구현을 시작한다.

## 목적

기존 HybridOCR 라벨링 웹 앱을 확장해 손글씨 이미지의 텍스트 줄 위치와 줄별 정답 전사를 함께 수집한다. 이를 통해 이미지 전체 전사만으로는 구분할 수 없던 텍스트 검출과 인식 성능을 각각 평가할 수 있게 한다.

## 현재 상태와 제약

- 코드 브랜치 `RADU/labeling`의 `labeling/`은 163장 이미지에 대한 협업 전사 앱이다. 이미지 보기, 작업 배정, 임시 저장, 검수 완료, GitHub 공유 저장, JSON/ZIP 내보내기를 제공한다.
- 현재 라벨은 이미지당 `text` 하나다. bbox 오버레이, bbox별 전사, bbox 전용 검수 상태는 없다.
- `src/cv/ocr_engine.py`의 PaddleOCR 엔진은 줄별 OCR 결과와 좌표를 반환한다. Vercel 앱은 Node.js이므로 OCR 추론은 브라우저 요청 안에서 실행하지 않는다.
- 공유 데이터 브랜치 `RADU/labeling-data`의 `live.json`에는 163개 항목이 있고, 이미지 전체 전사 기준 146개가 검수 완료, 1개가 작성 중, 16개가 미작성이다. 새 bbox 라벨링은 이 내용을 유지하면서 별도 상태로 시작한다.
- 사용자는 기존 전사를 **V1**, 새 bbox 전사를 **V2**로 분리해 저장하고 구분해 달라고 요청했다. V1은 현재 `labeling/data/live.json`을 그대로 사용한다. V2는 새 `labeling/data/live-v2.json`에 저장하며, 페이지 전체 전사 내용이나 상태를 복사하지 않는다.
- 웹 이미지 자산은 원본보다 축소된 WebP다. 결과 좌표에는 원본 너비·높이를 함께 기록하고, 화면 표시 좌표와 원본 좌표 사이를 변환한다.

## 목표

1. 기존 OCR 엔진으로 텍스트 줄 bbox 후보를 오프라인 생성한다. OCR 인식 문자열은 예측값으로 분리 보관하며 정답 라벨로 자동 복사하지 않는다.
2. HTML 화면에서 bbox를 원본 이미지 위에 겹쳐 보고, 박스를 추가·삭제·이동·크기 조정하고, 줄별 정답 문구와 읽기 순서를 편집할 수 있다.
3. 작성 중 저장과 검수 완료를 지원하고, 이미지별 JSON ZIP 및 통합 JSON으로 bbox 정답을 내보낸다.
4. V1 이미지 전체 전사와 그 검수 상태를 그대로 보존한다. V2 bbox 라벨은 163장 모두 별도의 미작성 상태에서 시작한다.
5. 화면에서 V1 전체 전사와 V2 bbox 전사를 구분해 열람·저장·내보내기 한다. V1의 텍스트를 V2의 정답으로 자동 복사하지 않는다.

## 제외 범위

- OCR 모델을 새로 학습하거나 Qwen 교정 알고리즘을 변경하지 않는다.
- 표 셀, 도형, 화살표 연결 관계 라벨은 다루지 않는다.
- 실시간 Python 모델 실행을 Vercel 서버에 추가하지 않는다.
- 기존 페이지 전체 전사를 bbox 단위로 자동 분할하거나 기존 라벨을 덮어쓰지 않는다.

## 검토한 접근법

1. **기존 협업 앱 확장 — 권장 기본안.** 기존 이미지 카탈로그·작업 임대·저장 API·내보내기를 재사용한다. OCR bbox는 로컬 명령으로 미리 만들고, 웹 화면에서 검수한다. 이미 운영 흐름이 있고 공유 저장을 유지하지만, OCR 후보 생성 전에 Python 의존성과 모델 가중치가 필요하다.
2. **별도 단일 HTML 도구.** 브라우저에서 박스를 수동 생성하고 JSON으로 저장한다. 가장 단순하지만 기존 협업 데이터와 저장 흐름이 분리되고, 후보 자동 생성이 없다.
3. **실시간 서버 OCR.** 웹에서 즉시 후보를 만든다. 사용 흐름은 짧지만 현재 Vercel Node 앱에 Python 모델 실행 환경과 모델 배포를 추가해야 한다.

사용자가 1번을 선택했다. bbox 단위는 손글씨 OCR의 검출·인식 평가를 분리하기 쉬운 텍스트 한 줄로 둔다.

## 동작 설계

### 후보 생성

- `src/cv/ocr_engine.py`의 기존 어댑터를 호출하는 오프라인 생성 명령을 추가한다. 초기 기본 엔진은 `paddleocrv6`로 하고, 기존 파이프라인의 `paddleocrvl16` 결과도 입력으로 재사용할 수 있게 한다.
- 생성 결과는 읽기 전용 `labeling/data/text-box-proposals.json` 후보 파일로 관리한다. 후보 파일에는 이미지 ID, OCR 엔진, 이미지 해시·크기, bbox, 예측 문자열, 신뢰도(제공되는 경우), 제안 버전을 기록한다. HTML 앱은 이 파일을 정적 데이터로 읽는다.
- OCR 예측은 별도 `prediction` 필드로 보관한다. 정답 `text` 필드는 비워 두고, 사용자가 명시적으로 복사할 때만 입력한다.
- 검수 시작 시 제안 박스를 편집 가능한 초안으로 가져온다. 후보 파일은 사람이 편집한 박스와 분리한다. 생성 명령은 기존 후보 파일을 기본 동작으로 덮어쓰지 않으며, 재생성은 새 버전 파일로 출력하고 앱 설정을 명시적으로 전환한다. 저장된 bbox 정답은 후보 재생성으로 변경하지 않는다.
- OCR 모델이나 가중치가 없어도 웹 편집기에서 수동으로 새 bbox를 추가할 수 있다.

### 웹 편집기

- 기존 이미지 선택·확대·이동·작업 잠금 흐름에 bbox 편집 모드를 추가한다.
- 선택된 줄의 박스와 텍스트 편집기를 연결한다. 이미지에서 박스를 선택하면 해당 줄이 강조되고, 목록에서 줄을 선택하면 이미지의 해당 위치를 확대한다.
- bbox는 원본 이미지 픽셀 기준 `[x1, y1, x2, y2]`로 저장한다. 화면에 표시할 때는 자산 크기와 원본 크기의 비율을 적용한다.
- 누락된 줄을 추가할 수 있고, 오검출 박스를 삭제할 수 있다. 모든 박스에 고유 ID와 읽기 순서를 둔다.
- 줄별 라벨 상태는 기존 이미지 전사 상태와 분리한다. 작업 진행률과 검수 필터도 bbox 상태를 기준으로 별도 표시한다.
- bbox가 없는 페이지를 검수 완료하려면 `no_text: true`를 명시한다. 빈 박스 목록만으로 완료 처리하지 않는다. 읽을 수 없는 줄은 `uncertain: true`와 메모를 남기고 미완료로 유지한다.

### 저장·내보내기

- 버전 선택기를 제공한다. 기존 페이지 전사 화면은 V1 데이터(`labeling/data/live.json`)를 읽고, 새 줄 bbox 작업은 V2 데이터(`labeling/data/live-v2.json`)를 읽고 쓴다. V2를 새로 초기화할 때에는 이미지 ID·이미지 메타데이터만 카탈로그에서 가져오고 모든 bbox 상태는 `unlabeled`로 둔다.
- V1과 V2의 API 작업·revision·저장 파일·내보내기 결과를 분리한다. V1의 현재 데이터 파일은 V2 저장으로 수정되지 않는다. 로컬 서버에서는 기존 `.runtime/state.json`을 V1로 유지하고 V2는 별도 상태 파일을 사용한다.
- V1의 기존 전사 내용을 V2 화면에서 참고 자료로 표시할 수는 있지만, V2 정답 텍스트로 자동 채우지 않고 V1임을 분명히 표시한다.
- 데이터 항목에 `bbox_annotation` 객체를 추가한다. 최소 필드는 `status`, `annotator`, `revision`, `notes`, `no_text`, `proposal_version`, `boxes`다. 박스에는 `id`, `bbox`, `text`, `prediction`, `order`, `uncertain`를 기록한다.
- bbox 저장 API는 기존 이미지 전체 `text`, `status`, `notes`를 수정하지 않는다. 기존 작업 임대와 충돌 방지 저장 원칙을 따른다.
- bbox 검수 완료 JSON 예시:

```json
{
  "schema_version": 1,
  "image_id": "hf-0000",
  "image_size": {"width": 3024, "height": 4032},
  "status": "verified",
  "annotator": "작성자",
  "no_text": false,
  "proposal_version": "paddleocrv6-<model-revision>",
  "boxes": [
    {"id": "line-0001", "bbox": [120, 248, 890, 316], "text": "정답 전사", "prediction": "OCR 후보", "order": 1, "uncertain": false}
  ]
}
```

`status: "verified"`에는 정답 텍스트가 있는 박스가 하나 이상 있거나, 사람이 확인하고 `no_text: true`를 설정한 경우만 허용한다.

- V1 내보내기는 기존 페이지 전사만 포함한다. V2 내보내기는 bbox 검수 완료본만 또는 전체 bbox 상태를 이미지별 JSON ZIP과 통합 JSON으로 제공하며, 버전 필드를 명시한다. 두 결과를 한 파일에 합치지 않는다.

## 논문 활용

라인 bbox와 전사를 확보하면 기존 저장소의 PaddleOCR-VL 단독 / Qwen 보정 비교를 확장해 검출 성능, 인식 CER/WER, 검출과 인식을 함께 반영한 성능을 구분해 평가할 수 있다. 5장 예비 결과는 가설 수립에만 사용하고 최종 주장의 근거로 사용하지 않는다. 데이터가 한 명의 작성자나 한 종류의 노트에 집중된다면 일반 한국어 손글씨 전반이 아니라 해당 기술 필기 도메인에 한정해 결론을 쓴다.

## 승인 후 구현 계획

설계 승인을 받았으며 V1/V2 분리 요구도 추가되었다. 구현 계획서를 작성하고, 버전별 저장소 분리·V2 초기 상태 → OCR 후보 생성기 → bbox 상태 저장 API → 이미지 bbox 편집 UI → 버전별 JSON/ZIP 내보내기 순서로 작업한다. 기존 `RADU/labeling-data`의 실제 `live.json`은 보존하고 V2 데이터는 별도 파일에 저장한다.
